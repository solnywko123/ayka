# DECISIONS.md — лог самостоятельных решений

Здесь фиксируются решения, принятые без явного указания в BRIEF.md, с обоснованием. Формат: дата, решение, почему.

## 2026-08-15 — Общий подход к выполнению

**Решение:** BRIEF.md выполняется как готовое ТЗ без дополнительного брейнсторминга с пользователем: раздел 17 прямо запрещает переспрашивать по мелочам, раздел 0 задаёт рабочие демо-данные, а раздел 18 задаёт порядок этапов. Решения по всем незакрытым вопросам принимаются самостоятельно и фиксируются здесь.

**Почему:** пользователь явно попросил не останавливаться с вопросами и работать по разделу 18 от начала до конца.

## 2026-08-15 — Тестирование без строгого TDD-цикла

**Решение:** код пишется, затем сразу покрывается тестами из раздела 15 (pytest для API, test_build.py и test_no_hardcoded_contacts.py для сайта), тесты прогоняются до зелёного состояния перед коммитом соответствующего этапа. Строгий red-green-refactor цикл по каждой мелкой функции не используется.

**Почему:** масштаб задачи — 14 этапов, полноценный сайт + API + админка за один проход. Формальный TDD на каждую строчку кратно увеличил бы время выполнения без выигрыша в качестве при таком объёме; при этом требование раздела 15 (тесты обязательны и зелёные) полностью выполняется.

## 2026-08-15 — Python окружение

**Решение:** используется `py` (Python Launcher, Python 3.13.4) вместо `python`/`python3` — на машине эти команды указывают на заглушку Microsoft Store. Виртуальное окружение `.venv` создаётся через `py -m venv .venv`. В Makefile и README команды используют `py`/`.venv` явно, без опоры на `python` в PATH.

**Почему:** `python`/`python3` в PATH ведут на неустановленную заглушку Windows Store и завершаются с ошибкой; `py`-лаунчер найден и указывает на реально установленный Python 3.13.4 (BRIEF.md требует 3.12+, 3.13 совместим).

## 2026-08-15 — Git identity

**Решение:** используется уже настроенная глобальная git-идентичность пользователя (найдена через `git config user.email/user.name`), локальный override в репозитории не создаётся.

**Почему:** git config уже содержит валидные global user.name/user.email, локальная переустановка не требуется и не запрашивалась.

## 2026-08-15 — `make` недоступен локально

**Решение:** `Makefile` создаётся по спецификации (раздел 3, 13, 14, 19.3) и будет работать в Linux/CI/деплой-окружениях (Netlify/Render, где `make`/POSIX-шелл есть по умолчанию). Локально на этой Windows-машине `make` не установлен, поэтому для самопроверки в ходе разработки команды из Makefile прогоняются напрямую (`py site/build.py`, `py -m pytest` и т.д.), а не через `make`.

**Почему:** `where make` не находит исполняемый файл на машине; переустановка make не входит в объём задачи и не блокирует выполнение остальных требований BRIEF.md.

## 2026-08-15 — Шрифт: Manrope

**Решение:** выбрана гарнитура Manrope (вариативный шрифт, SIL Open Font License 1.1 — свободное самостоятельное хостинг и распространение). Файлы `.woff2` скачаны с Google Fonts (одна вариативная версия на подмножество: latin, cyrillic, cyrillic-ext — они покрывают все нужные буквы, включая киргизские Ә/Ө/Ү/Ң) и лежат в `site/static/fonts/`, подключены через `@font-face` с `font-display: swap`, без CDN в проде.

**Почему:** раздел 4 требует гарнитуру с хорошей кириллицей на выбор (Inter/Manrope/Onest), self-hosted `.woff2`. Manrope даёт современный геометричный вид, хорошо читается в крупных заголовках с `clamp()`, лицензия позволяет самостоятельный хостинг.

## 2026-08-15 — Одинаковые URL-слаги во всех языках

**Решение:** структура путей (`/uslugi/{slug}/`, `/rayony/{slug}/`, `/ceny/`, `/o-nas/`, `/otzyvy/`, `/kontakty/`, `/blog/{slug}/`) одинакова для `ru`, `ky`, `en` — меняется только языковой префикс. Слаги не переводятся.

**Почему:** BRIEF.md даёт точные русские слаги только для `/ru/`, для `ky`/`en` слаги не оговорены. Единые слаги упрощают переключатель языка (раздел 5.5: «ведёт на ту же страницу в другом языке») и `hreflang`-разметку, снижают риск рассинхронизации при добавлении новых страниц.

## 2026-08-15 — Маппинг 6 услуг на 4 типа калькулятора

**Решение:** 6 страниц услуг используют 4 типа калькулятора (`maintenance/general/post_renovation/post_move` из `pricing.json`) так: генеральная→general, после ремонта→post_renovation, поддерживающая→maintenance, офисы→maintenance + property_type=office (предустановлено), химчистка мебели→maintenance + акцент на addon `sofa_seat`/`carpet_per_m2`, мытьё окон→maintenance + акцент на addon `windows_per_sash`.

**Почему:** в разделе 0 `pricing.json` заданы только 4 базовые ставки за м², а в разделе 5.2 перечислено 6 услуг — часть из них (мебель, окна) в реальности продаются как «допуслуги», а не отдельный тариф за м². Это соответствует и разделу 6 (окна/диван/ковёр — в списке «доп. услуги», а не типов уборки).

## 2026-08-15 — Проверка калькулятора/формы без браузера

**Решение:** визуальная проверка калькулятора и формы заявки в реальном браузере не выполнена — расширение Claude in Chrome не подключено в этой сессии, а иных браузерных инструментов нет. Вместо этого выполнена структурная проверка всей сборки: локальный HTTP-сервер поднят и отдаёт страницы (200 OK), автоматическая проверка отсутствия битых внутренних ссылок (2347 ссылок, 0 битых), валидности JSON-LD на всех 74 HTML-файлах, наличия title/description/canonical/ровно одного h1 на каждой странице (кроме технической `index.html`-редиректа). Формула `calculator.js` построчно сверена с формулой из раздела 6 BRIEF.md.

**Почему:** нужно быть честным о границах проверки — рантайм-поведение JS (реальный клик по калькулятору, реальная отправка формы) не подтверждено визуально в браузере, это должно быть перепроверено вручную владельцем или в отдельной сессии с подключённым браузерным инструментом перед стартом рекламы.

## 2026-08-15 — `from __future__ import annotations` несовместим с `@limiter.limit`

**Решение:** в файлах роутеров, где применяется декоратор `slowapi`'s `@limiter.limit(...)` (`api/app/routers/quote.py`, `api/app/routers/leads.py`), НЕ используется `from __future__ import annotations`.

**Почему:** при живом запуске обнаружено: с отложенным вычислением аннотаций (PEP 563) FastAPI пытается резолвить forward-ref параметров эндпоинта через `__globals__` обёрнутой декоратором функции — а `slowapi.Limiter.limit` подменяет функцию на обёртку, определённую в модуле `slowapi`, из-за чего `QuoteRequest`/`LeadCreate` там не резолвятся и приложение падает при старте с `PydanticUndefinedAnnotation`. Прямые (не отложенные) аннотации это обходят.

## 2026-08-15 — Относительный `DATABASE_URL` резолвится от `api/` как CWD

**Решение:** `DATABASE_URL=sqlite:///./dev.db` (не `./api/dev.db`) — предполагается, что `uvicorn`/`alembic`/`pytest` запускаются с рабочей директорией `api/` (как и написано в README: `cd api && ...`).

**Почему:** SQLAlchemy резолвит относительный путь sqlite от текущей рабочей директории процесса, а не от расположения файла настроек; единообразный CWD = `api/` исключает путаницу с `api/api/dev.db`.

## 2026-08-15 — Формула цены проверена end-to-end, но не через реальный JS

**Решение:** после поднятия API локально (`uvicorn`, SQLite) вручную сверены результаты `POST /api/v1/quote` и `POST /api/v1/leads` с ручным расчётом по формуле раздела 6 для нескольких наборов параметров (включая все множители и скидку) — совпадение точное. Формальное автоматизированное сравнение с `calculator.js` (раздел 15: «совпадение результата фронтового и бэкового расчёта») по-прежнему не может исполнить сам JS (нет Node.js и браузера в этом окружении, см. запись выше) — вместо этого `api/tests/test_pricing.py` (этап 12) будет тестировать `api/app/pricing.py` напрямую по значениям из общего `pricing.json`, а идентичность формул с `calculator.js` обеспечивается тем, что это один и тот же алгоритм, построчно перенесённый в оба файла (сверено вручную), с перекрёстными комментариями в обоих файлах.

**Почему:** прозрачность о том, что именно проверено автоматически, а что — только сверкой кода вручную.

## 2026-08-15 — Cookie `Secure` отключается только при `BUILD_ENV=dev`

**Решение:** флаг `Secure` на JWT-cookie админки (`api/app/security.py::cookie_kwargs`) выставляется в `True` всегда, кроме `BUILD_ENV=dev` — тогда `False`.

**Почему:** обнаружено при живом тестировании входа в админку: с `Secure=True` браузер (и `http.cookiejar` в тесте) не отправляет cookie обратно по обычному `http://`, а локальная разработка (в том числе на этой машине) идёт без TLS — вход в админку не работал вообще (редирект обратно на `/login` после успешной аутентификации). В проде (Render, HTTPS) `BUILD_ENV=prod` и `Secure=True` всегда, как требует раздел 7.

## 2026-08-15 — JSON API админки и серверный HTML используют общий `admin_service.py`

**Решение:** `api/app/routers/admin.py` (JSON API под `/api/v1/admin/*`, раздел 7) и `api/app/admin_ui/router.py` (серверный Jinja2-интерфейс под `/admin/*`, раздел 9) не дублируют логику и не дёргают друг друга по HTTP — оба вызывают общие функции `api/app/admin_service.py` (`list_leads`, `get_lead`, `update_lead`, `export_csv`, `compute_stats`), работающие прямо с ORM-сессией.

**Почему:** в разделе 3 структуры репозитория `routers/admin.py` и `admin_ui/` — разные файлы/модули, значит это разные вещи (JSON API и HTML-страницы), а не одно и то же под двумя именами; общий сервисный слой — стандартный способ не плодить дублирующуюся бизнес-логику.

**Проверено вручную** (локальный сервер, SQLite): логин через HTML-форму и через JSON `/api/v1/admin/login`, дашборд и список заявок рендерятся с реальными данными, смена статуса/заметки/ответственного через форму сохраняется и отражается в истории событий, экспорт CSV отдаёт корректные заголовки и все строки, `/api/v1/admin/stats` считает счётчики и потенциал верно, неаутentифицированный доступ к `/admin` редиректит на логин, к `/api/v1/admin/*` — 401 с единым форматом ошибки.

## 2026-08-16 — Добавлен `psycopg2-binary` в `api/requirements.txt`

**Решение:** в `api/requirements.txt` рядом с `psycopg[binary]==3.2.3` (psycopg v3) добавлен `psycopg2-binary==2.9.10`.

**Почему:** деплой на Render упал с `ModuleNotFoundError: No module named 'psycopg2'`. Причина — `DATABASE_URL`, который отдаёт Render через `fromDatabase.connectionString` (см. `deploy/render.yaml`), приходит в виде обычного `postgresql://...` без суффикса диалекта, а SQLAlchemy 2.0 по умолчанию резолвит схему `postgresql://` в диалект `psycopg2`, а не `psycopg` v3 (тот требует явного `postgresql+psycopg://`). Раз мы не переписываем URL, который формирует сам Render, надёжнее держать оба драйвера установленными: `psycopg2-binary` — потому что его понимает SQLAlchemy без изменений в конфиге по умолчанию для стандартной `postgresql://` строки, `-binary` — чтобы не требовались системные библиотеки сборки (`libpq-dev` и т.п.) в Docker-образе (`python:3.12-slim`). `psycopg` v3 оставлен как есть — им явно пользуется `docker-compose.yml`/`docker-compose.prod.yml`, где URL собирается вручную с префиксом `postgresql+psycopg://`.

Проверено: `pip install psycopg2-binary==2.9.10` ставится чисто на `python:3.12`-совместимом окружении без ошибок сборки, `import psycopg2` работает, полный набор `api/tests` (45/45) зелёный после добавления зависимости.

**Решение:** владелец запросил уход от бирюзово-коралловой палитры BRIEF.md раздела 4 к более яркой, «притягивающей» схеме на основе 4 цветов. Полностью переписаны CSS-токены в `site/static/css/main.css` (light + dark режимы), с сохранением семантики имён переменных:

Это осознанный выбор, а не «пятый цвет»: если сделать primary одним из 4 ярких цветов, весь текст/шапка/футер/иконки автоматически станут таким же цветом, что и акценты — получится ровно тот эффект «детского конструктора», от которого предостерегал владелец. - **`--color-accent-*`** — единственный неизменный цвет CTA-кнопок по всему сайту: насыщенный синий (#2563eb / #1d4ed8 hover). Выбран из 4 цветов не случайно: красный конфликтует по смыслу с `--color-danger` (ошибки форм), жёлтый физически даёт низкий контраст с белым текстом на кнопке, зелёный конфликтует с `--color-success`. Синий — единственный из четырёх, который не пересекается по смыслу ни с одним семантическим цветом (успех/ошибка/предупреждение) и даёт устойчиво хороший контраст.
- **Новые токены `--color-brand-{red,yellow,green,blue}`** (+ пары `-glyph` и `-100`) — для декоративного использования (иконки-бейджи, звёзды рейтинга), НЕ для текста и НЕ для кнопок. У каждого «-glyph» — затемнённый тон, специально подобранный так, чтобы держать контраст ≥4.5:1 на своей же бледной «-100» подложке (проверено вручную по формуле WCAG, см. ниже).
- **`--gradient-brand`** — диагональ красный→жёлтый→зелёный→синий, используется только в hero, финальном CTA и как тонкая 4px декоративная полоса-разделитель (граница футера сверху, через `border-image`). Больше нигде на сайте градиент не встречается — сознательно не «заливал» им карточки услуг целиком (это дало бы 6 разноцветных кричащих карточек на одном экране, что и есть предостережение владельца про «неравнозначность 4 цветов одновременно»); вместо этого палитра проявляется точечно — как цвет бейджа иконки на карточке (см. ниже).
- **Нейтралы** (`--color-bg`, `--color-surface`, `--color-text` и т.д.) — сдвинуты с тёплых бежевых тонов на холодные, с лёгким синим оттенком, чтобы гармонировать с новым синим accent/primary (не «дефолтный серый», а осознанно подобранный под палитру, как и просит хороший дизайн).

**Контраст (WCAG, посчитано по формуле относительной яркости, не на глаз):**

- Самое узкое место — белый текст поверх градиента в hero/final-cta на участке жёлтого (самый светлый цвет из четырёх). ## 2026-08-16 — Критический баг: название компании невидимо в тёмной теме браузера

**Решение:** владелец сообщил «не видно даже название компании». Причина — architectural: `--color-primary-600/700/900` использовались в CSS сразу в двух несовместимых ролях — как ЦВЕТ ТЕКСТА (лого, пункты меню, хлебные крошки, ссылки в статьях, и т.д. — 15+ мест) и как ФОН (кнопки, футер, подвал калькулятора — 7 мест, всегда с белым текстом поверх). Токен не был переопределён для тёмной темы вообще — то есть в светлой теме это тёмно-чернильный цвет, и в тёмной теме браузера он остаётся ровно тем же тёмно-чернильным цветом. Для фоновых случаев это нормально (тёмный фон + белый текст работает в любой теме), но для текстовых — катастрофа: например, лого в шапке (`color: var(--color-primary-900)`) на фоне шапки (`--color-surface`, которая в тёмной теме сама становится тёмной) даёт контраст **1.03:1** — фактически невидимо. Посчитано формулой WCAG, не на глаз.

Фикс — разделил роли:
1. Все 7 фоновых случаев (`.skip-link`, `.btn-primary`, `.btn-primary:hover`, `.logo__mark`, `.step::before`, `.calc-result`, `.site-footer`) переведены на литеральные hex-значения (`#1e2230`, `#12151b`) вместо переменных — эти фоны обязаны оставаться тёмными в любой теме, раз на них лежит белый текст.
2. Отдельно нашёл и починил ещё 2 скрытых случая той же ловушки: `.hero/.final-cta .btn-accent` (белая кнопка с текстом `--color-primary-900`) и `.btn-whatsapp` (зелёная кнопка с тем же текстом) — их фон ВСЕГДА фиксированный (белый / зелёный WhatsApp-бренд) независимо от темы сайта, поэтому текст на них тоже обязан быть литералом, а не переменной — иначе при попытке «светлить» переменную для читаемости текста в шапке эти две кнопки сломались бы в обратную сторону (светлый текст на белом/зелёном фоне). ## 2026-08-18 — Починен sticky-хедер (наслаивался на контент) и убраны все упоминания «оплаты после проверки результата»

**1. Sticky-хедер.** Владелец сообщил, что на `/ru/biznes/` (и, как выяснилось, вообще на всех страницах) хедер при скролле не прилипал к верху корректно, а «зависал» в промежуточном положении, наслаиваясь на контент. Причина: при добавлении переключателя сегментов «Частным лицам/Бизнесу» (см. запись выше про Royal Blue редизайн) блок `.site-header__segment` был вложен ВНУТРЬ `<header class="site-header">`, у которого `position: sticky` сочетается с фиксированной `height: var(--header-height)` (72px, рассчитана на один ряд). С учётом вложенного второго ряда (сегмент-переключателя) реальная высота содержимого хедера стала больше 72px, но `overflow` по умолчанию `visible` — лишние ~36px просто визуально вылезали за пределы sticky-контейнера, из-за чего часть хедера (`.site-header__inner` с навигацией) не была корректно «прилеплена» и оказывалась в неправильном месте при скролле, наслаиваясь на контент под ней. Ancestor'ы (`html`/`body`/`main`) проверены — `overflow: hidden`/`transform` на них нет, конфликта родителя со sticky не было, дело именно в высоте самого `<header>`.

Фикс: `.site-header__segment` вынесен из `<header>` — теперь это отдельный, не-sticky блок перед хедером (скроллится вместе со страницей, как и было задумано изначально); сам `<header class="site-header">` вернулся к исходной однорядной структуре с точным соответствием высоты 72px и корректно работающим `position: sticky`. Исправление в общем партиале `templates/partials/header.html`, применяется ко всем страницам сайта одинаково (проверено на `dist/ru/index.html`, `dist/ru/kontakty/index.html`, `dist/ru/biznes/index.html` — везде `.site-header__segment` теперь идёт раньше `<header>` в DOM).
